# Lingxing local-product snapshot acceptance

From a clean checkout with Docker Compose, Bash, Python 3, curl and OpenSSL, run:

```sh
python3 -m unittest discover -s tools/smoke/data-integration-wp2-8
bash tools/smoke/data-integration-wp2-3/run.sh lingxing
```

The simulated product-list responses use the public offset, length, total and product fields. The fixture exercises a two-page export, preserves decimal costs and leading zeroes in SKUs, and completes all pages before creating an export object. Empty results are recognized; publishing an empty replacement awaits a business decision. [Lingxing local product list](https://apidoc.lingxing.com/new/api-docs/Product/ProductLists/)

An upstream batch ID identifies one completed export. The fixture supplies two synthetic batches as distinct NDJSON objects. A real S3 Connector reads each with scoped credentials and commits it into a raw dataset. The test passes the batch ID, original Connector run, raw transaction, expected row count and checksum to the handoff. The handoff re-reads the committed file, verifies its checksum and submits the original bytes to the dedicated product dataset using a stable Dataset commit key. Redeliver the first batch after the second is visible to observe the original receipt. Reusing its ID with different bytes must return HTTP 409. Retrying a manual Connector extraction creates a separate run; the replay in this test starts at the committed export handoff.

One cost Pipeline then reads the published product snapshots, not the raw batches, through the Pipeline graph API. Its graph is a pinned dataset input, a `select` of `sku` and `cg_price`, and an output to another dataset. The same Pipeline runs three times, pinned by dataset, branch, version and transaction to v1, v2 and v1 again while v2 is the branch head. Each run is checked against its saved graph and the receipt of its input node. The run receipt also gives the transaction RID of the committed output resource. That RID is the Pipeline's own name, `pipeline-run:<run id>:output`, and not the transaction of the Dataset service. A read-only reader lists the output versions, finds the one Dataset transaction each run added and reads it: its `metadata.transaction_rid` must repeat the Pipeline resource RID and its `metadata.pipeline_rid` the Pipeline. That is how a run is linked to its output version. The reader then lists and downloads the file of that transaction and reconciles the bytes line by line and value by value with a fixed expectation and SHA256: three costs for v1, two for v2 where `0007` keeps its place with a new cost, `N4` is new and `W-2` and `D3` are gone, and a replay equal to the first output. Both values stay strings, `0007` and `0.00` included. product-report.json records the Dataset transaction of each input and output under `input_transaction` and `output_transaction`, and the Pipeline resource RID under `pipeline_output_transaction_rid`.

Every product snapshot is published with one formal input contract: the fields `cg_price`, `id`, `product_name` and `sku` in that order, the id `LONG` and the other three `STRING`, none nullable. An independent reader without write permission asks the formal versioned schema of v1 and v2 on main, bound to the transaction that cut each version and to the content hash it expects, and checks that the answer names the dataset, branch, version and transaction, lists the declared fields and hashes them to the same digest. It derives the same contract from the bytes it downloads, so the SKU and the cost are strings at the source and in the contract. v1 answers the same schema again while v2 is the head. A version asked with the transaction of the other version is refused with 409 `dataset_schema_transaction_mismatch`, one asked for another content hash with 412 `dataset_schema_content_hash_mismatch`, and the same user in another organization with 403 or 404. Each of the three Pipeline runs pins `expected_schema_hash` next to branch, version and transaction. The Pipeline service proves that hash against the Dataset service as the caller before it reads a row. The same input pin is refused twice, on a Pipeline of its own each time, and publishes nothing either time: once with a pin that names v1 together with the transaction that cut v2, which the Dataset service refuses with 409, and once run by the same user in another organization, whose read of the product dataset the Dataset service refuses with 404. Saving the graph accepts both. Each run fails at the input node before a row is read, cancels the two nodes after it, commits no output resource and leaves the output versions as they were.

A batch published before the contract existed was sent without a schema, and that request is not rewritten. The Dataset service fingerprints the exact request, so the request a batch is delivered with follows its first publication. The test publishes the first batch to a separate dataset as it was sent then: the same request replays to the original receipt, and the same batch key sent with the contract schema is refused with 409 `IDEMPOTENCY_KEY_CONFLICT` and creates no version. That version keeps its rows readable by version and answers no versioned schema, 422 `dataset_schema_format_unsupported`, so it cannot be bound to the contract. To bind it, publish the batch again under the contract as a new version.

The evidence directory contains product-report.json, both source batch files, two downloaded product files, each versioned schema answer, the saved graph and run of each Pipeline run, three downloaded cost files, the graph and run of each refused input, the refused replay of the earlier batch and its unsupported schema answer, binary checksums and Compose image IDs. The Docker project and its temporary identities are isolated. The report records each upstream batch, both Dataset transactions and, for each Pipeline run, its input version and transaction, the schema hash it is bound to, output version and transaction, and the SHA256 a downstream consumer can expect. Under `schema` it lists the contract, its content hash and every schema read with its status and artifact; under `legacy` the earlier batch, its two replays and its unsupported schema read; under `pipeline.refusals` the saved input, node states and errors of the two refused runs. A real approved Lingxing export is still needed to validate source ownership and production field mapping: the source pages are simulated, and the services that carry the data are real. The browser checks of the noon case are not part of this run.

## Downstream replay of the three archived transactions

The downstream consumers of the three v3 outputs are the sync clients of `ontology_sync.py`. Each archived transaction is delivered twice through its client into `object-database-service` on a real Cassandra store: `ProductCost` from lingxing, `OrderLinePrice` from noon and `SettlementLine` from Amazon. The inputs are the copies embedded in `ontology_sync.py`; the evidence directory of an earlier run is not read. From a clean checkout of the revision under test, with Docker Desktop running, run from the repository root:

```sh
(
set -e
EVIDENCE=${EVIDENCE:-$(mktemp -d)}
echo "evidence: $EVIDENCE"
docker image inspect cassandra:5.0 >/dev/null 2>&1 || docker pull cassandra:5.0
docker image inspect golang:1.26.11 >/dev/null 2>&1 || docker pull golang:1.26.11
docker volume create of-wp2-8-downstream-gomod
mkdir "$EVIDENCE/bin"
docker run --rm -v "$PWD":/src:ro -w /src -v of-wp2-8-downstream-gomod:/go/pkg/mod -v "$EVIDENCE/bin":/out \
    -e CGO_ENABLED=0 -e GOFLAGS="-trimpath -buildvcs=false" golang:1.26.11 \
    go build -o /out/object-database-service ./services/object-database-service/cmd/object-database-service
git rev-parse HEAD
openssl dgst -sha256 "$EVIDENCE/bin/object-database-service"

python3 tools/smoke/data-integration-wp2-8/ontology_sync_replay.py --type ProductCost --bin-dir "$EVIDENCE/bin" --output "$EVIDENCE/product-cost-replay.json"
python3 tools/smoke/data-integration-wp2-8/ontology_sync_replay.py --type OrderLinePrice --bin-dir "$EVIDENCE/bin" --output "$EVIDENCE/order-line-price-replay.json"
python3 tools/smoke/data-integration-wp2-8/ontology_sync_replay.py --type SettlementLine --bin-dir "$EVIDENCE/bin" --output "$EVIDENCE/settlement-line-replay.json"
)
```

The block stops at the command that fails, so a failed build is never followed by a replay, and it prints its evidence directory first. `$EVIDENCE` is a new directory for every run; set it to keep the evidence of one run. A directory whose `bin` exists is refused, so the binary of an earlier run is never read. The two images of `ontology_sync.compose.yaml` are pulled only when they are missing, and the first build downloads the modules of `go.mod` and `go.sum` from `proxy.golang.org` into the volume `of-wp2-8-downstream-gomod`. The binary is built with the `-trimpath` of `make build-services`, statically and without VCS stamping, for Linux and the architecture of `golang:1.26.11`, arm64 on Apple Silicon. Each replay starts the Compose stack of `ontology_sync.compose.yaml` with that binary, removes it on exit and returns 0 only when every scenario passed. `revision` in each file is the revision of the archived input and not of the code under test, which is the one `git rev-parse HEAD` printed. In each of the three files expect `passed` to be true and `stack.binary_sha256` to be the SHA256 above, so all three runs are bound to one binary. Under `scenarios.replay_twice.deliveries` the first delivery holds three results with `created` true and the second the same three object ids with `created` false. The objects read back after the first delivery, after the replay and after the refused change are the same three, one per row and each with its archived value: `by_sku` in both deliveries and `after` of `other_content_is_rejected` for `ProductCost`, `by_item_nr` in both deliveries and the same `after` for `OrderLinePrice`, and `lines` in both deliveries and in `changed_total_is_rejected` for `SettlementLine`. In `settlement-line-replay.json` the second and third line are the order and the refund of order `000-0000000-0000004` and SKU `DEMO-SKU-D4`, two object ids with totals `7.44` and `-7.44`, and `total` is `59.57`, the exact decimal sum of the three lines, after each delivery and after the refusal. The evidence is in `$EVIDENCE`: the binary and the three files.

## This round's v3 delivered downstream

The replays above read the copies embedded in `ontology_sync.py`. Those are the v3 outputs of one earlier run, and they hold the same SKUs, costs and SHA256 as the v3 of every later round and as the v1 of each round, which replays the same input: neither the values nor the hash of the bytes says which transaction, version and file they came from. What names the v3 of one round is the receipt of the Pipeline run that published it. `bash tools/smoke/data-integration-wp2-3/run.sh lingxing` therefore does not stop after the three runs. It builds `object-database-service` next to the three services, starts the Compose stack of `ontology_sync.compose.yaml` with that binary, pulling its two images when they are missing, and runs the delivery entry while its own Dataset service is still up:

```sh
python3 tools/smoke/data-integration-wp2-8/ontology_sync_published.py --state DIR --dataset-base URL --endpoint URL [--tenant ID]
python3 tools/smoke/data-integration-wp2-8/ontology_sync_published.py --state DIR --endpoint URL --tenant ID --verify-only
```

`--state` is the evidence directory the lingxing smoke printed. The read-only account is the bearer in `WP34_TOKEN`, the same account without any permission that reads the published versions above, and it sends GET requests only; `--dataset-base` defaults to `WP34_DVS`. The tenant is the organization of the round unless `--tenant` names one. The entry reads the saved receipt of the run that published v3 and follows it: the one committed resource of the run names the output dataset and, in its `transaction_rid`, the handle the Pipeline gave the transaction; exactly one transaction of that dataset repeats the handle in `metadata.transaction_rid`, and it names the same Pipeline and the same output hash as the receipt; the version that cut it holds one file, which the entry lists by that transaction, downloads from the signed address without sending the bearer there, and hashes itself. It writes product-cost-source.json, the dataset, version, transaction, file and SHA256 it found, and product-cost-v3.ndjson, the bytes. It then delivers the three rows once through the conditional put of `ontology_sync.py` and reads the tenant back through the list route and then the detail route of each listed object.

One assertion decides the exit code. The tenant is accepted when it holds exactly three objects, when the id of each is the one the client derives from the tenant, the type, the transaction of the receipt and the SKU it holds, when each holds `0007`/`0.00`, `W-2`/`9.25` or `D3`/`17.40`, and when its `_source` repeats the dataset, version, transaction, file and SHA256 of that read and the line of its SKU in that file. Two objects that swapped their complete properties keep the same ids and costs and agree with the SKU each names; the id of each object is what places its row, so they are refused. The entry prints one JSON report with the delivery and that readback and returns 0 when the tenant is accepted. A redelivery of the same key and content is accepted the same way by #90, so the same command run again, also after a restart of the downstream process, returns 0 and reports `created` 0; an object of the same key with another content stops the delivery with exit code 1, and a tenant that also holds another source is refused. The smoke runs the command twice, as two processes with the same command: the first must exit 0 having created three objects, the second exit 0 having created none and read the same three objects back, and both must have located the same source. Each report is kept on its own.

The smoke then delivers three other sources the same way, each into a tenant of its own, and reads each back with `--verify-only`, which judges a tenant against product-cost-source.json without syncing anything or asking the Dataset service. A refusal counts only once that tenant is shown to hold exactly the other source and nothing else: the delivery ended without error, for the archived transaction with exit code 0, and the tenant holds one object per row of that file, three or two, each with the id, the cost and the `_source` of its row, which is what the same assertion finds when it is given that source and its rows instead of those of this round. Each must then be refused with exit code 1 by the same assertion, and for its identity alone: the `_source` problems must name exactly the attributes in which the source differs from this round, and the id set must be refused as well. The archived transaction is delivered by the default call of `ontology_sync.py`; it shares the values and the SHA256 of this round and differs in dataset, transaction and file, so no cost is named for it. The v1 this round published is located read-only from its own receipt; it shares the dataset, the values, the bytes and the SHA256 of v3 and differs in version, transaction and file, so no cost is named for it either. The v2, located the same way, shares the dataset alone and differs in version, transaction, file and SHA256. Last, the tenant of the round is read back again and must still hold the same three objects.

The evidence of this step is in the same directory. product-cost-downstream.json holds under `deliveries` the command, exit code and whole report of each of the two processes, under `refused` for each other source its tenant, the source it was meant to receive and the rows of its file, how it was delivered, what the tenant holds, whether that is exactly that source, which attributes differ from this round and the exit code and problems of its readback, and under `checks` every check with its outcome; `passed` is true only when all of them passed. product-cost-delivery-1.json and product-cost-delivery-2.json are the two reports, each with its own readback, product-cost-refused-<source>.json the readback of each refused tenant, product-cost-refused-archived_transaction-delivered.json the report of the default call, product-cost-readback.json the last readback, and product-cost-source.json and product-cost-v3.ndjson what the read-only account found and downloaded. `services.sha256` includes the object service binary, and `stack` in product-cost-downstream.json its SHA256 and the Cassandra release. `downstream` in product-report.json keeps the summary: the source, the exit code and created count of each delivery, and for each refused source how many objects its tenant holds, whether they are exactly that source, its exit code and the attributes that differ.

`bash tools/smoke/data-integration-wp2-3/run.sh noon` delivers the v3 of the noon order lines the same way, by the same entry with `--type OrderLinePrice`: the order line number `item_nr` is the key of a row and its currency and unit price its values, the tenant is the `organization` of `noon-report.json`, and the evidence is written under `order-line-price-` in place of `product-cost-`. The archived noon transaction and the v1 and v2 of the noon round are refused as the three sources above are, and the five order lines of v2 are told from the three of v3 by their identity alone. [The noon README](noon/README.md#this-rounds-v3-delivered-downstream) holds the details. `bash tools/smoke/data-integration-wp2-3/run.sh amazon` delivers the v3 of the Amazon settlement lines the same way, by the same entry with `--type SettlementLine`: a settlement line has no key property of its own and its object is keyed by `_source.file` and `_source.line` as in #92, its settlement id, type, order id, SKU and total are its values, read as exact decimals, the tenant is the `organization` of `amazon-report.json`, and the evidence is written under `settlement-line-`. [The Amazon README](amazon/README.md#this-rounds-v3-delivered-downstream) holds the details. `Kind` holds what differs between the three types, the reader, the assertion, the entry and the run being theirs in common; without `--type` the entry is the lingxing one and keeps the commands and the files of #95.

## The three objects through the edge gateway

The three objects a round delivers are read and written by other services through `edge-gateway-service`, not through the object service's own port. `run.sh` accepts that boundary in the round's own stack, while it is still up and holds the three objects: nothing is delivered again and no id is typed in. From the same clean checkout run:

```sh
bash tools/smoke/data-integration-wp2-3/run.sh lingxing-gateway  # ProductCost, a row named by its SKU
bash tools/smoke/data-integration-wp2-3/run.sh noon-gateway      # OrderLinePrice, a row named by its order line number
bash tools/smoke/data-integration-wp2-3/run.sh amazon-gateway    # SettlementLine, a row named by its line in the file
```

Each is its source's round, with the same checks and the same files as `run.sh lingxing`, `noon` or `amazon`, and then one more step. `object-database-service` and `edge-gateway-service` are built from the checkout; the gateway runs as one container on the network of the round's Cassandra stack, published by Docker on a loopback port it picks and routed to that object service; `ontology_sync_gateway.py` runs the scenarios, one for the three types by their `Kind`. The sources without the suffix run as before.

Five accounts ask, each an ordinary HS256 identity the smoke fixture of business-platform-p1 mints with a key generated for this run and written nowhere: the tenant's reader (no permission) and writer (`ontology:write`), another synthetic organization's reader and writer, and a reader of the all-zero organization. They ask only the adapter's six routes and send no tenant header of their own:

- A1, the tenant's reader lists, fetches each of the three ids and queries (POST `…/objects/query` is a read). Each answer holds exactly the three objects as the direct read of the downstream consumer holds them: as many rows as objects, as many distinct ids, `total` 3 and no other id, so a row the gateway repeats is refused; every business property of each row and its six `_source` attributes. A fraction is read as the exact decimal the gateway answered, so a settlement line's `total` is held to the direct read digit for digit and is never a float nor a string.
- A2, the same reader tries to create, update and delete: each is refused 403 `object_write_forbidden`, and the direct read holds what it held.
- A3, the other organization's reader is answered an empty list and 404 for each of this tenant's ids; its writer creates an object (201) that its own reader fetches and that the direct read holds in its own partition alone; this tenant's direct read holds what it held.
- A5, the all-zero organization's reader is answered its empty list, 200 and not `organization_required`.
- A4, last, the tenant's writer creates a temporary object (201), updates it (200) and deletes it (204), each seen by the tenant's reader. Afterwards the gateway answers 404 for its id, so does the object service asked directly, and the list answers the three objects again, three rows and three ids with `total` 3, read five times in the four seconds after the delete and recorded each time.

The temporary objects carry the properties `WRITES` holds for the type and a `note`; a settlement line's total is a whole number there.

`<prefix>-gateway.json` in the evidence directory is the record: the gateway's container id, label, binary SHA256 and image id; the five accounts as labels, organizations and permissions and never a token; `expected_ids` and `control`, the three ids and their properties as the first delivery report of the round gave them; `gateway_requests`, the 26 requests with each status and answer body and `Authorization: Bearer <redacted>`; `a1_by_row`, what the direct read, the list, the detail and the query each hold for a row; the `verdicts` of A1 to A5; and `checks`, each with its scope, gateway, object store or setup. An error is recorded with the key and any token taken out. `<prefix>-downstream.json` keeps under `gateway` the outcome alone (the evidence file, `passed`, `checks` as passed and total, `requests`), and the smoke's report the same under `downstream.gateway`; without the suffix neither key exists.

The run passes only when every check passed: the 15 of `<prefix>-gateway.json` and one more in `<prefix>-downstream.json`; otherwise the smoke stops with a non-zero exit. On exit the gateway container is removed by id, and with it only what carries the label of this run: a container Docker created and could not start included.
